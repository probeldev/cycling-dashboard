# cycling-dashboard

Личный дашборд велотренировок из FIT-файлов с велокомпа Cycplus C2. Список тренировок по годам/месяцам, деталка с графиками и картой, BLE-синхронизация с устройством — одним бинарником, без внешних зависимостей.

![Список тренировок](images/main.jpeg)
![Деталка тренировки](images/details.jpg)

## Возможности

- **Дерево тренировок**: год → месяц → тренировки. В строке тренировки — средняя мощность и TSS, месяц показывает сплит по типу (`улица — N км, X ч; станок — X ч, Y ккал`), суммарный TSS и средний IF (квадратичное среднее `sqrt(Σ(IF²·t)/Σt)`)
- **Деталка тренировки**: длительность, общее время и паузы, дистанция, скорость, каденс, мощность, пульс, калории. Для мощности — IF, TSS, VI и средняя «в работе»; если `no_power_sec + suspect_dropout_sec` больше 5% времени в движении (`duration_sec`), показывается жёлтый бейдж «данные с пропусками» с расшифровкой в подсказке (у тренировок без поверметра бейджа нет)
- **Распределение по диапазонам**: время в бакетах по каденсу / скорости / мощности / пульсу (горизонтальные бар-чарты). Для мощности накат — отдельный бакет `0 Вт · накат`, а под баром подписаны обе базы: время педалирования и время вместе с накатом
- **График мощности** по времени для тренировок с поверметром
- **Карта маршрута** на OpenStreetMap (Leaflet) для уличных поездок
- **Поиск** по имени и дате
- **Имена тренировок** — задаются вручную
- **Определение станка**: нет GPS, либо размах трека < 1 км (C2 пишет дрейфующие координаты даже на станке), либо FIT помечен как `indoor_cycling`. Ручной override на деталке
- **Страница прогресса** (`/progress`): PMC на сегодня (CTL/ATL/TSB со словесной трактовкой), TSS за текущую неделю и за 4 недели (включая текущую), график TSS/CTL/ATL/TSB (периоды 30/90/180/365 дней), heatmap-календарь года по дневному TSS, MMP-график (последние 30/90/365 дней поверх предыдущего периода), карточка CP / W' / оценка FTP по MMP, таблица зон по неделям с долей низкой интенсивности (ориентир поляризованной модели 80/20)
- **Геймификация**: калории за месяц переводятся в «пиццы пепперони» — 1 пицца = 2400 ккал (Domino's Пепперони Делюкс 100, L, 950 г)
- **BLE-синхронизация** с Cycplus C2 (представляется как `M2_XXXX`) — кнопка в вебе, качает только новые файлы
- **Инкрементальный импорт** по хешу файла — повторный запуск подхватывает только новое

## Запуск

Нужен Go 1.26+ (см. `go.mod`) и macOS/Linux (BLE-синх — только macOS, см. ниже).

```sh
go run ./cmd/server
# или бинарник:
go build -o cycling-dashboard ./cmd/server && ./cycling-dashboard
```

Флаги:

| Флаг | По умолчанию | Описание |
|------|--------------|----------|
| `-dir` | `tracks` | папка с FIT-файлами |
| `-db` | `cycling.db` | путь к SQLite |
| `-addr` | `127.0.0.1:8080` | адрес сервера |
| `-reimport` | `false` | перечитать все `.fit` из `-dir` заново (после изменений парсера). Обычные бэкфиллы (`subsport`, `np_version`, `metrics`, `mmp`) при старте отрабатывают сами |

Откроется `http://127.0.0.1:8080`.

## API

JSON-эндпоинты для программного доступа к данным тренировок (используются, в т.ч., AI-скиллом для разбора поездок). Базовый URL — `http://127.0.0.1:8080`.

### `GET /api/workouts`

Список всех тренировок от новых к старым. Элементы — полные объекты тренировки:

```json
[
  {
    "ID": 308,
    "StartTime": "2026-10-29T20:48:57+03:00",
    "Name": "Ramp Test",
    "Duration": 3021000000000,
    "DistanceKm": 0,
    "HasGPS": true,
    "Trainer": true,
    "Override": null,
    "SubSport": "generic",
    "AvgSpeedKmh": 23.7,
    "MaxSpeedKmh": 27.6,
    "AvgCadence": 80,
    "MaxCadence": 134,
    "AvgPower": 96,
    "MaxPower": 155,
    "NormPower": 97,
    "NPVersion": 4,
    "BikeID": 0,
    "Bike": "",
    "IF": 0.622,
    "TSS": 32.4,
    "VI": 1.01,
    "AvgPowerActive": 96,
    "CoastingSec": 17,
    "NoPowerSec": 513,
    "SuspectDropoutSec": 0,
    "ElapsedSec": 3020,
    "PauseSec": 0,
    "WorkKJ": 240.3,
    "AvgTemp": 24.6,
    "HasTemp": true,
    "MetricsVersion": 1,
    "AvgHR": 0,
    "MaxHR": 0,
    "Calories": 290,
    "AscentM": 0,
    "DescentM": 1,
    "HasPower": true,
    "FTP": 156,
    "FTPKind": "trainer",
    "WeightKg": 75
  }
]
```

- `Duration` — в **наносекундах** (Go `time.Duration`)
- `FTP` / `WeightKg` — штампы профиля на момент тренировки (от них считаются зоны, чтобы история не пересчитывалась при обновлении профиля)
- `FTPKind` — источник `FTP`: `trainer` (станковый FTP; для улицы — fallback, если уличного ещё нет) или `outdoor` (уличный FTP). Пустая строка, если FTP не задан
- `SubSport` — подсорт из FIT-сессии (`generic`, `indoor_cycling`, `road`, `mountain`, …). Пустая строка, если устройство его не записало
- `IF` / `TSS` / `VI` / `WorkKJ` — метрики нагрузки (формулы — в «Технических заметках»). **`null`** — данных нет (например, у тренировки без поверметра); число — значение известно. Служебный `HasWork` в JSON не отдаётся: отсутствие данных видно по `WorkKJ: null`, а валидный ноль работы — по `WorkKJ: 0`
- `AvgPowerActive` / `CoastingSec` / `NoPowerSec` / `SuspectDropoutSec` / `ElapsedSec` / `PauseSec` — целые секунды/ватты; `CoastingSec`/`PauseSec` = 0 — валидные нули (наката/пауз не было), у остальных 0 означает отсутствие данных
- `AvgTemp` / `HasTemp` — средняя температура записей, °C: `AvgTemp: 0` при `HasTemp: true` — честные 0 °C; у старых сэмплов температуры нет — заполняется после `-reimport`
- `MetricsVersion` — версия формул метрик
- `BikeID` / `Bike` — назначенный велосипед и его имя (`0` / пустая строка — не указан)
- `AvgHR`/`MaxHR` = 0 — датчик пульса не был подключён

### `GET /api/workouts/latest`

Последняя по дате старта тренировка — тот же объект, что в списке. Удобна как health-check (`curl -sf …/api/workouts/latest`).

### `GET /api/workout/{id}`

Детали одной тренировки по ID (формат объекта — как выше). 404, если нет.

### `GET /api/workout/{id}/dist`

Распределение времени по бакетам, посчитанное по сырым сэмплам из БД (без бакет-усреднения: иначе на записи 2 Гц нули мощности смешались бы с педалированием и накат бы пропал). Ключи — только для метрик с данными:

```json
{
  "power":   [{"label": "0 Вт · накат", "secs": 818, "pct": 0, "pctTotal": 15.7},
              {"label": "Z1 · 0–87.4",  "secs": 232, "pct": 5.3, "pctTotal": 4.5},
              {"label": "Z2 · 87.4–118.6", "secs": 548, "pct": 12.5, "pctTotal": 10.5}],
  "powerBase": {"coastSecs": 818, "pedalSecs": 4379, "totalSecs": 5197},
  "cadence": [{"label": "0–40",       "secs": 73,   "pct": 0, "pctTotal": 0},
              {"label": "50–60",      "secs": 309,  "pct": 0, "pctTotal": 0}],
  "speed":   [{"label": "0–10",       "secs": 247,  "pct": 0, "pctTotal": 0},
              {"label": "15–20",      "secs": 1706, "pct": 0, "pctTotal": 0}]
}
```

Фрагмент реального ответа для тренировки 418 (в ответе все 8 бакетов мощности и все бакеты остальных метрик). Ключа `hr` в нём нет: у неё не был подключён пульсометр, а ключи отдаются только для метрик с данными (`hr` появится у тренировок с датчиком).

- `power` — зоны Коггана Z1–Z7 в ваттах от FTP-штампа тренировки (если FTP не задан — фиксированные диапазоны 0–50…400+ Вт). Пороги в подписях — реальные, без округления до целых (`87.4–118.6` при FTP 156); правая граница в зону не входит. Первым всегда идёт бакет **`0 Вт · накат`** — свободный ход (мощность ноль при живом поверметре)
- `cadence` — бакеты по 10 об/мин (0–40 … 100+)
- `speed` — 0–10, дальше по 5 км/ч (10–15, 15–20, …, 40+)
- `hr` — бакеты по 10 уд/мин
- `secs` — суммарное время в бакете
- `pct` / `pctTotal` — доля бакета в процентах: `pct` от времени педалирования, `pctTotal` от общего времени вместе с накатом. Поля есть у всех бакетов (у `cadence`/`speed`/`hr` — нули, чтобы клиент мог суммировать без проверок на `undefined`). У бакета наката `pct` всегда 0 (накат — не педалирование), сумма `pct` по «педалирующим» бакетам и сумма `pctTotal` по всем ≈ 100
- `powerBase` — две базы времени мощности: `coastSecs` (накат), `pedalSecs` (педалирование, power > 0), `totalSecs` (их сумма). Процент времени в зонах исторически считался от `pedalSecs` — `powerBase` показывает, что за база

Отличать накат от дропаута: `power == 0` при `HasPwr` — это накат, он попадает в нулевой бакет. Отсутствие мощности (поверметр отвалился, `HasPwr: false`) не попадает ни в один бакет. Нули по каденсу / скорости / пульсу по-прежнему не учитываются.

Время записи — интервал до следующего сэмпла; записи с одинаковым `ts_offset` (например, запись 2 Гц) делят интервал до следующего различного offset поровну. Разрыв больше 5 с — это либо пауза (1 с), либо прореживание записи при движении (полный интервал, но не больше 60 с — `ridedata.MaxGapSec`). Признаки в порядке приоритета: (1) прирост `distance_m` на границах разрыва, если дистанция известна с обеих сторон (перед авто-паузой в записи остаётся последняя «ещё ехавшая» скорость, а расстояние уже не растёт); (2) скорость на границе от 1 км/ч — ехали; (3) если ни дистанции, ни скорости нет — педалирование: есть мощность или каденс — ехали, нет — стояли. Правило одинаковое для всех бакетов — и для наката, и для зон мощности.

### `GET /api/workout/{id}/samples`

Сэмплы для графиков. По умолчанию бакет-усредняются до ~500 точек:

```json
[
  {"Offset": 0, "Power": 95, "HasPwr": true, "Cadence": 78, "HasCad": true,
   "HR": 132, "SpeedMs": 6.5, "Lat": 0, "Lon": 0, "HasPos": false, "AltitudeM": 0,
   "HasAlt": false, "DistanceM": 0, "HasDist": false, "TempC": 17, "HasTemp": true}
]
```

| Параметр | По умолчанию | Описание |
|----------|--------------|----------|
| `max` | `500` | верхняя граница числа точек, от 1 до 200000 — возвращается **не больше** `max` |
| `raw` | `0` | `raw=1` — отдать все сэмплы как есть, без бакет-усреднения (для внешнего анализа нужны честные медиана и пики); `max` при этом игнорируется и не валидируется, а тренировка длиннее 200000 сэмплов — 400 |

Некорректный параметр (`max=abc`, `max=0`, `max=-5`, `max` больше потолка, `raw=maybe`) — **400** с текстом ошибки.

- `Offset` — секунды от старта тренировки
- флаги `HasPwr`/`HasCad`/`HasPos`/`HasAlt`/`HasDist`/`HasTemp` — были ли данные в сэмпле (нулевые значения без флага = «нет данных», а не 0)
- `TempC` — температура записи, °C (в FIT — sint8)
- если `max` меньше числа сэмплов, точки — бакеты: `Offset` и значения усредняются по попавшим в бакет записям (offset — среднее, а не `MIN`: точка смещается к центру бакета и не садится на край длинной паузы); у известной тренировки без сэмплов ответ `[]`, у неизвестной — 404

```sh
# все 5281 сэмплов тренировки без усреднения
curl -s 'http://127.0.0.1:8080/api/workout/418/samples?raw=1' | jq length
```

### `GET /api/workout/{id}/mmp`

Power-duration (MMP): лучшие средние мощности по окнам. Отдаются только окна, которые влезают в запись; неизвестный id — 404.

```json
[{"secs": 1, "watts": 436}, {"secs": 5, "watts": 376.6}, {"secs": 60, "watts": 218.1},
 {"secs": 300, "watts": 169.4}, {"secs": 1200, "watts": 153.7}]
```

Окна: 1, 2, 5, 10, 20, 30, 60, 120, 300, 600, 900, 1200, 1800, 2700, 3600, 7200 с. В окно входят все записи: `power > 0` даёт работу, накат (`power == 0`) — только время и честно разбавляет среднюю. Вес — `ridedata.Timings.Secs`; пауза обрывает сегмент, поэтому окно не склеивает мощность до и после остановки. Дропаут датчика (`HasPwr == false`) заполняется последним валидным значением (**fill-forward**, как в NP) — иначе его время выпадало из окна и длинное окно могло оказаться выше короткого. Дропауты до первой валидной мощности заполнять нечем — сегмент начинается с первого валидного значения.

Окно — ровно `window` секунд реального времени: запись, пересекающая правую границу, входит частично; окно не может начинаться с записи длиннее самого окна (иначе «1-секундный пик» стал бы средним за 60 с). Хранится в `power_records`, версия — `mmp_version`; заполняется при импорте и бэкфилле при старте.

### `GET /api/records?period=30d|90d|365d|all`

Лучшие значения по каждому окну MMP за период (по умолчанию `all`; мусор → 400). При равенстве рекорд принадлежит более ранней тренировке.

```json
[{"secs": 5, "watts": 376.6, "workoutId": 418, "date": "2026-10-31T10:56:59+03:00", "name": ""},
 {"secs": 60, "watts": 218.1, "workoutId": 418, "date": "2026-10-31T10:56:59+03:00", "name": ""}]
```

- `previous` — лучшее за предыдущий период такой же длины (для `all` не отдаётся); поле появляется, только если в предыдущем периоде были тренировки с мощностью. Формат: `{"secs": 5, "watts": 370.1, "workoutId": 311, "date": "…", "name": ""}`
- периоды считаются от сегодняшнего дня (`30d` — последние 30 дней включая сегодня), а не от последней тренировки

### `GET /api/workout/{id}/prs`

В каких периодах тренировка держит рекорд по каждому окну: `{"5": ["all", "365d", "90d", "30d"], "60": ["all"]}`. Периоды по убыванию значимости; неизвестный id — 404.

### `GET /api/cp?period=30d|90d|365d|all`

Модель критической мощности по MMP периода: линейная регрессия `W = CP + W'/t` по окнам 120–1200 с.

```json
{"cp": 153.8, "wPrime": 6211, "r2": 0.867, "points": 5, "ftpEst": 146, "lowConfidence": true}
```

Это фит по **огибающей MMP** периода (лучшее по каждому окну; на текущих данных 120/300/600 с держит ramp-тест 52, остальные — 418), поэтому W' может быть завышен, а R² — ниже, чем у одной тренировки. Для сравнения, по кривой только 418: `cp 152.5, wPrime 4122, r2 0.974`.

- `cp` — Вт, `wPrime` — Дж, `r2` — качество фита, `points` — сколько окон использовано (нужно ≥3)
- `ftpEst = 0.95 × W(1200 с)`, только если окно 20 мин есть в данных; иначе `null`
- `points < 3` или неположительные CP/W' — `cp`/`wPrime`/`r2` = `null`, `lowConfidence: true`
- `r2 < 0.95` — числа отдаются, но с флагом `lowConfidence: true`; порог проверяется по неокруглённому R². Это оценка по огибающей MMP, а не физиологический тест

### `GET /api/timeline?from=YYYY-MM-DD&to=YYYY-MM-DD`

Дневной ряд за `[from, to]` включительно (по умолчанию — 180 дней до сегодня; максимум 3660 дней; мусор или `from > to` → 400). День тренировки — локальная дата `start_time` (в БД время хранится в UTC).

```json
[{"date": "2026-10-31T00:00:00+03:00", "tss": 118.17, "hours": 1.47, "distanceKm": 27.83,
  "rides": 1, "trainerRides": 0, "outdoorRides": 1,
  "ctl": 5.111, "atl": 27.449, "tsb": -9.976}]
```

PMC (форма/усталость/свежесть):
- `CTL_t = CTL_{t-1} + (TSS_t − CTL_{t-1}) / 42`
- `ATL_t = ATL_{t-1} + (TSS_t − ATL_{t-1}) / 7`
- `TSB_t = CTL_{t-1} − ATL_{t-1}` — на начало дня, до нагрузки этого дня
- EWMA греется с даты самой ранней тренировки (или с `from`, если истории нет), а в ответ попадают только дни `[from, to]` — поэтому CTL/ATL/TSB на дату не зависят от выбранного окна (30 дней или 365 — числа одинаковые)
- пустые дни идут с TSS=0 и участвуют в EWMA, поэтому пропуски не разрывают кривую

### `GET /api/weeks?n=12`

Последние `n` недель (пн–вс, включая текущую; по умолчанию 12, максимум 52; мусор → 400):

```json
[{"start": "2026-10-26T00:00:00+03:00", "tss": 219.7, "hours": 3.7, "distanceKm": 27.8,
  "rides": 4, "trainerHours": 2.2, "outdoorHours": 1.5,
  "zones": [1433, 5210, 1338, 1490, 723, 440, 111],
  "lowPct": 61.8, "highPct": 25.7, "grayPct": 12.5}]
```

- `zones` — секунды в зонах Коггана Z1–Z7; `lowPct` = Z1+Z2, `grayPct` = Z3, `highPct` = Z4–Z7 (доли от времени в зонах)
- зоны хранятся в `workout_zones` и считаются тем же `ridedata.PowerTime`, что `/dist` и импорт; заполняются при импорте и в бэкфилле при старте

### Пример: разобрать последние тренировки

```sh
# id и даты всех тренировок
curl -s http://127.0.0.1:8080/api/workouts | jq '.[] | {id: .ID, date: .StartTime, name: .Name}'

# детали + зоны по мощности для конкретной
curl -s http://127.0.0.1:8080/api/workout/308 | jq '{avg: .AvgPower, norm: .NormPower, ftp: .FTP}'
curl -s http://127.0.0.1:8080/api/workout/308/dist | jq '.power'
```

## Синхронизация с велокомпом

1. Включи Cycplus C2, положи рядом с компьютером
2. Закрой приложение Cycplus на телефоне (оно держит BLE-соединение)
3. Нажми **«Синхронизировать с велокомпом»** в шапке дашборда

Скачанные файлы падают в `-dir`, после синка база обновляется автоматически. Протокол — Nordic UART Service (`6e400001-…`), Go-порт оригинального `cycSync.py`.

**Про Docker**: BLE не заведётся — на macOS Docker живёт в VM без доступа к Bluetooth. Программа и так один статический бинарник, докерить незачем.

## Технические заметки

- **Скейлы FIT**: `tormoder/fit` отдаёт сырые значения, скейлы из FIT-профиля применяются в `internal/importer` руками (время ×1000, дистанция ×100, скорость ×1000). Меняя парсер — не потерять это
- **NP (нормализованная мощность)**: считается по Коггану и только если устройство само его не отдало. Скользящее среднее берётся за **30 секунд по `ts_offset`**, а не за 30 сэмплов — при записи не 1 Гц окно в сэмплах плывёт. Дальше x⁴ → среднее → ⁴√. И скользящее среднее внутри окна, и итоговое среднее считаются по времени (вес — `ridedata.Timings.Secs`): при неравномерной записи (smart recording, 2 Гц) NP не перекашивается в сторону плотно записанных участков. Дропауты поверметра заполняются последним значением (fill-forward); окно обрывает только разрыв-стоянка — по тому же правилу `internal/ridedata`, что и распределения (дистанция → скорость → педалирование), а прореженная при движении запись окно не рвёт. Версия алгоритма пишется в `workouts.np_version` (`NPVersion` в API); при старте сервера тренировки со старой версией пересчитываются из сохранённых сэмплов (одной транзакцией), без перечитывания FIT. Тренировки без сэмплов, без валидной мощности или с одними нулями при device-NP > 0 не трогаются — device-NP не затирается нулём (все нули при ненулевом NP похожи на залипший датчик), они остаются с прежней, меньшей актуальной версией до появления данных. Полный ре-импорт из файлов — флаг `-reimport`
- **`tinygo.org/x/bluetooth`**: vanity-домен tinygo.org периодически отдаёт битый go-get; в `go.mod` стоит `replace` на `github.com/tinygo-org/bluetooth` — при обновлении зависимости проверить, нужен ли он ещё
- **Температура**: `record.temperature` (sint8, invalid 0x7F) пишется в `samples.temperature`, среднее по непустым — в `workouts.avg_temp` (0 °C и отрицательные — валидные значения, NULL только при отсутствии данных). Старые сэмплы температуры не имеют: чтобы заполнить историю, нужен `-reimport` (файлы Cycplus её содержат)
- **Велосипеды**: таблица `bikes` (имя, тип, active) с идемпотентным сидом «Trek SL 1000» (road), «Октопус» (fixed), «Trek 820» (mtb); `workouts.bike_id` — пользовательское поле, ре-импорт его не трогает. Станок — не велосипед: тип тренировки уже отмечен флагом `trainer`, а `bike_id` указывает на конкретную раму (или NULL). На деталке велосипед выбирается селектом, на `/progress` — пробег/часы/поездки по велосипедам
- **Раздельные FTP**: в `profile_history` есть `kind='ftp'` (станок) и `kind='ftp_outdoor'` (улица). Штамп `workouts.ftp_w` выбирается по флагу `trainer` (с учётом `trainer_override`): станок — `ftp`, улица — `ftp_outdoor`, а если уличного значения ещё нет — fallback на `ftp`. В `workouts.ftp_kind` пишется, откуда взято значение (`trainer`/`outdoor`): это источник FTP, а не тип тренировки. На деталке источник подписан: «(станок)», «(улица)», а для fallback — «(станок, уличный не задан)»; в `/profile` при отсутствии уличного FTP показывается, что используется станковый. Смена `ftp` инвалидирует метрики только станковых тренировок, смена `ftp_outdoor` — только уличных (кроме случая fallback: тогда смена станкового FTP задевает и улицу). Переключение типа тренировки (улица/станок) в той же транзакции перештамповывает FTP и пересчитывает IF/TSS — без рестарта. Ре-импорт учитывает `trainer_override`: тип для выбора FTP берётся из override, а не из FIT
- **Метрики нагрузки** (колонки `workouts.if/tss/vi/...`, в API — `IF`, `TSS`, `VI`, `AvgPowerActive`, `CoastingSec`, `NoPowerSec`, `SuspectDropoutSec`, `ElapsedSec`, `PauseSec`, `WorkKJ`, `MetricsVersion`) считаются при импорте после штампов профиля; время — из `ridedata.Timings`, того же источника, что NP и распределения:
  - `if = NP / ftp_w` (NULL, если NP=0 или FTP=0)
  - `tss = duration_sec × NP × IF / (ftp_w × 3600) × 100` (NULL без NP/FTP)
  - `vi = NP / avg_power` (NULL, если avg_power=0; от FTP не зависит)
  - `avg_power_active` — средняя только по `power > 0`; `coasting_sec` — время `power == 0`; `no_power_sec` — время без данных (`power IS NULL`); `suspect_dropout_sec` — `power == 0` при `cadence > 0` (похоже на отвал датчика)
  - `elapsed_sec` — `TotalElapsedTime` из FIT-сессии; `pause_sec = elapsed_sec − duration_sec`, отрицательное — 0; `work_kj` — `TotalWork` из сессии (джоули → /1000), если он записан и больше нуля, иначе `Σ(power × Secs) / 1000`
  - invalid-маркеры таймеров (`0xFFFFFFFF`) отсекаются: иначе `duration_sec` стал бы ~49.7 дней и TSS взорвался
  - `MetricsVersion` — версия формул; при старте строки со старой версией пересчитываются из сэмплов одной транзакцией, а `elapsed_sec`/`work_kj` дочитываются из FIT-сессии (если файл на месте, иначе остаются NULL). TSS считается от `duration_sec`, поэтому заполняется и у тренировок без сэмплов, если есть NP и FTP
  - при изменении FTP (`BackfillProfileStamps`) или NP (`SetNormPowers`) у затронутых строк сбрасывается `MetricsVersion` — метрики пересчитываются сразу после правки профиля и при следующем старте; если FTP или NP исчез, IF/TSS обнуляются (VI пересчитывается — он от FTP не зависит). Вес на метрики не влияет и их не инвалидирует
  - запись профиля, пересчёт штампов и метрик идут одной транзакцией: ошибка пересчёта откатывает всё и отдаёт 500, а не «сохранено»
- **Осиротевшие сэмплы** (`workout_id=0` от старого импорта, а также ссылки на удалённые тренировки) не видны ни одному запросу и чистятся идемпотентной миграцией при старте (`DELETE` + лог количества). Если таблица `workouts` пуста, чистка пропускается с предупреждением — иначе недосозданная база потеряла бы все сэмплы. На чистой базе удаляется 0 строк и строка в лог не пишется
- **`workouts.subsport`** заполняется из FIT-сессии при импорте. Для уже импортированных тренировок при старте сервера отрабатывает бэкфилл (`importer.BackfillSubSport`, по образцу `store.BackfillProfileStamps`): он перечитывает FIT только у строк с `subsport_checked = 0` и ставит этот флаг даже если в файле subsport нет, поэтому повторный старт файлы не читает, а пользовательские `name` и `trainer_override` не перетираются. Если файла нет на диске, строка с предупреждением помечается проверенной (значение `subsport` при этом сохраняется) — иначе чтение и предупреждение повторялись бы каждый старт; вернувшийся файл подхватит `-reimport`. Если нет и каталога (похоже на неверный `-dir`), строку не помечаем — после исправления пути бэкфилл отработает сам; существующая, но пустая папка трактуется как «файлов больше нет». Остальные ошибки чтения (битый FIT, права) оставляют строку непроверенной — они могут быть временными
- **Cycplus C2 пишет `subsport = generic` даже для станка**, поэтому тип тренировки определяется не по нему, а по GPS и размаху трека (см. «Определение станка»)
- **SQLite**: WAL и `busy_timeout=5000` (через DSN — драйвер применяет pragma к каждому соединению пула), поэтому параллельные записи (например, несколько POST профиля) ждут освобождения блокировки, а не падают с `SQLITE_BUSY`
- **Сэмплы хранятся все** (266 414 записей на 54 тренировки в текущей базе), API по умолчанию прореживает их до 500 точек для графика (`?max=N` — свой лимит, `?raw=1` — все сэмплы без усреднения); распределения считаются по полным данным, время сэмпла = интервал до следующего (паузы обрезаются, прореженная при движении запись — нет)
- Треки в `tracks/` — личные данные, в git не коммитятся (`.gitignore`)

## Структура

```
cmd/server/        точка входа, флаги
internal/importer  FIT → SQLite (tormoder/fit, скейлы, детект станка)
internal/ridedata  общие правила времени записей и пауз (NP и распределения)
internal/store     SQLite-схема, миграции, запросы
internal/web       chi-хендлеры, шаблоны (embed), API графиков, sync-менеджер
internal/blesync   BLE-клиент для Cycplus C2 (tinygo.org/x/bluetooth)
tracks/            FIT-файлы (не коммитятся)
```
